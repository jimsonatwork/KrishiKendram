## 1. Purpose

God Mode is the authoritative administrative root of KrishiKendram. It is not a dashboard that merely reports backend state. It is the governed control plane through which system truth, application behavior, security, authorization, configuration, lifecycle, infrastructure, recovery, and delegated administration are defined.

**Control loop:** centralize ownership → expose governed control → validate impact → snapshot → apply → health-check → audit → recover if required.

God Mode must refer to the canonical KrishiKendram registry and configuration sources and must not create a second competing authorization or configuration engine.

## 2. Authority model

### God Mode / Root Node
The default God identity is a protected singleton: `jimson@jimson.jimson`. Its credential is generated by the application, rotated on restart and defined integrity/tamper events, and never committed to Git. Testing artifacts are `rootnodepass.txt` and `rootnodepass.kkt` under `backend/config/god-mode/`. The God identity cannot be deleted through ordinary CRUD; only God may change permitted identity details. God can administer every governed platform capability.

### Super Admin
Created through the normal user workflow. Capabilities are delegated by God Mode.

### Admin / Cluster Head
Operate only within God-defined role/resource/action/workflow policies.

### General users
Farmers, vendors, sellers, buyers, integrators, manufacturers, service providers, government agencies and future categories are governed through the same policy model.

## 3. Canonical God Configuration Registry

Every God-controlled setting should carry: stable ID, category, name, description, current value, type, default, allowed values/schema, editable flag, God-only flag, risk level, dependencies, dependents, validation rules, restart requirement, approval requirement, snapshot-before-change, audit policy, lifecycle, version, owner/source, last actor and timestamp.

Existing backend services remain enforcement authority; God Mode calls them rather than bypassing them.

## 6. Runtime and infrastructure

God controls or diagnoses application start/stop/restart, health, backend/frontend processes, Node/runtime, Docker containers/images/ports/volumes/restart policy, dependencies, logs and readiness. Destructive operations require confirmation. Volume deletion is never part of ordinary restart.

## 7. Database and connections

Govern provider, host, port, database, username, connection status, Prisma status, migration/schema status, pool health and backup/restore state. Secrets stay masked and are referenced through controlled ownership rather than raw connection strings.

## 8. Modules, registry and resources

For each module/resource expose identity, description, lifecycle, enabled state, dependencies, dependents, routes, resources, fields, capabilities, permissions, validation, flags, audit and recovery snapshot. God may enable, disable, configure, deprecate, restore and inspect where safe mutation contracts exist.

## 9. Authorization and delegation

Authorization is **Role × Module × Resource × Action × Scope × Field Policy**. Actions include view/create/update/delete/archive/restore/approve/verify/suspend/re-enable/configure/administer. God defines the matrix; delegated users operate inside it. No frontend-only authorization engine may override backend authorization.

## 10. Field policy and validation center

God controls required/optional/nullable, format, normalization, length/range, regex, uniqueness, duplicate email/mobile and allow/warn/block behavior, including screen/module-specific overrides.

## 11. Themes and application administration

God controls themes, defaults, colors, typography, density, animations/performance mode, navigation density, minimized navigation, landing page, table/pagination defaults and UI flags.

## 12. Navigation administration

Navigation objects carry label, icon, route, parent, order, enabled state, visible roles, permission, feature flag, lifecycle and dependencies.

## 13. Feature flags

Support enabled, disabled, beta, admin-only, God-only and scheduled states for future AI, localization, marketplace, integrations, analytics and experimental modules.

## 14. User lifecycle and approval workflows

Lifecycle: Created → Pending → Verified → Active → Suspended → Re-enabled → Archived. God defines who can create, approve, verify, suspend, re-enable, modify, soft-delete and finalize deletion. High-risk actions may require multiple approvers and escalation.

## 16. Snapshot and recovery contract

Before significant configuration/destructive mutation:

**validate → dependency analysis → snapshot → apply → health-check → audit**

Snapshots capture affected configuration, registry, permissions, validation, lifecycle, navigation/flags, relevant database configuration and version metadata.

Recovery:

**inspect → compare → validate → restore → health-check → audit**

A restore creates a new snapshot so rollback remains reversible.

## 17. Audit and history

Every governed mutation records actor, action, timestamp, source, module, resource, before/after state, reason/context, dependency impact, snapshot ID and result/error. Deletion, approval, suspension, configuration, credential, registry, infrastructure and recovery operations require first-class audit evidence.

## 18. Dependency graph

Before risky changes, show affected parents, children and dependents. Example: Database connection → Prisma → Auth → Users → Farms → Marketplace → Audit. Changes that invalidate required dependencies may be blocked.

## 19. Diagnostics

Health checks cover application, database, Prisma, Docker, filesystem, registry, authorization, credentials, routes, frontend, backend, environment, migrations and snapshots. Protected route-test operations expose method/path/module/auth/permission/status/dependencies/last check/last error.

## 20. Implementation rules

1. Extend canonical sources; do not create competing configuration sources.
2. Do not hardcode settings God Mode is expected to control.
3. Backend enforcement remains authoritative.
4. UI uses canonical API/service contracts.
5. Significant mutation is validated, dependency-aware, snapshotted and audited.
6. Secrets never appear in ordinary diagnostics.
7. Restart never deletes data or volumes.
8. Canonical root remains `/home/jj/Dev/KrishiKendram`.
9. Restart-required changes state that requirement before apply.
10. Recovery is reversible.
11. God Mode is protected and never an unauthenticated backdoor.
12. God Mode governs the whole KrishiKendram platform.
